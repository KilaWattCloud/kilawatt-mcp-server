# Contributing to kilawatt-mcp-server

Thank you for your interest in contributing to kilawatt-mcp-server! We welcome all contributions, whether they're bug reports, feature requests, documentation improvements, or code changes.

## Getting Started

### Prerequisites

- Node.js 18.x or higher
- npm 8.x or higher

### Setup

1. Fork the repository and clone it locally
2. Install dependencies:

```bash
cd kilawatt-mcp-server

# Install dependencies
npm install

# Run the syntax and MCP protocol tests
npm run check

# Start the server (requires KILAWATT_API_KEY)
KILAWATT_API_KEY=kw_live_your_key npm start
```

## Code Style Expectations

This is a plain JavaScript (ES6 modules) project without build, compilation, or type-checking steps. Please:

- Write clear, readable code with meaningful variable names
- Add comments for complex logic
- Follow the existing code style in the repository
- Use const for immutable values and let for reassignment

## Testing Your Changes

Before submitting a pull request, please:

1. Run `npm test` and `npm run check`
2. Verify the server starts with `npm start` and a valid `KILAWATT_API_KEY`
3. Test your changes locally with an MCP client if possible

## Adding a tool

1. **Define it.** Tools are defined in code, and each definition has a `name`, a `description`, an `inputSchema` and, where it applies, `annotations`. Add the definition next to the related tools:
   - `index.js`: `DEPLOY_GPU_NODE` and the `DISCOVERY_TOOLS` array (`get_capacity`, `get_platform_status`, `get_pricing`, `get_resume_info`, `resume_job`)
   - `x402.js`: the `X402_TOOLS` array
2. **Handle the call.** Route the tool name in the `CallToolRequestSchema` handler in `index.js`. Validate every argument before any network call, and return errors with `isError: true`. Never include an API key or private key in tool output.
3. **Add a test.** Tests start the real server over stdio with `fetch` replaced by `test/mock-fetch.js`, so no test calls a live endpoint. Add any new endpoint to `test/mock-fetch.js`. Then add cases to `test/discovery.test.js` (or a new `test/*.test.js` file added to the `test` script in `package.json`) that cover the request URL, method and headers, input validation with no network call, error responses, and that no key appears in output. Update the tool list check in `test/discovery.test.js`.
4. **Regenerate the tool reference.** Run `npm run docs` and commit the updated `docs/TOOLS.md`.
5. **Update the docs.** Add the tool to the README and `CHANGELOG.md`.

## Generated docs

`docs/TOOLS.md` is generated by `npm run docs` from the tool definitions the server returns for `tools/list`. Do not edit it by hand. `npm run check` fails if it is out of date, so run `npm run docs` after changing any tool name, description, input schema or annotation.

## Pull Request Process

1. Run `npm test` and `npm run check`
2. Verify the server starts with `npm start` and a valid `KILAWATT_API_KEY`
3. If you changed a tool, run `npm run docs` and commit `docs/TOOLS.md`
4. Update documentation if you've changed functionality
5. Add a clear description of what your PR does
6. Be responsive to review feedback

## Releases

Releases are published manually by a maintainer running the "Publish to npm" workflow (`workflow_dispatch`) from the Actions tab. The workflow requires the `NPM_TOKEN` repository secret. Do not publish the package from a local machine.

## Reporting Issues

If you find a bug or have a feature request, please open an issue with:

- A clear, descriptive title
- A detailed description of the problem or request
- Steps to reproduce (for bugs)
- Expected vs. actual behavior
- Your environment (Node.js version, OS, etc.)
